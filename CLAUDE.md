# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Personal portfolio site (GitHub Pages, `ilyaeis.github.io`). It is a single-page WebGL experience: a tap-driven "journey" that flies a glowing comet trail from an intro screen (name, the line "3D reconstruction and computer vision · Giraffe360 · Riga", and a "skip to work · resume" link pair) through the three trait words (it traces and spirals around them, no tap), then to the work first: the Giraffe360 rock (universe `work`), then a dive over the cut ceiling into a Gaussian splat of a real apartment (universe `rnd`, Giraffe360 R&D): six object stops, each a procedural splat object with a halo ring, joined by indoor flights through the doorways. It leaves over the window wall to the three education rocks (universe `education`: school, AI Talent, RTU), then warps into an endless, snaking tunnel of glowing strands: three project stops sit on its centreline (each a live visualization), and three smaller fly-by projects hang inside it between them. The tunnel turns almost a full circle, so the warp out comes home behind the apartment, and the comet dives through the roof to the contact landing in the living room. On the way it swings past dim, slowly spinning strange-attractor "galaxies" (scenery). At each rock, object and project stop the camera shifts the stop to one side, and an HTML panel shows the milestone text on the other side. No framework, no build step, no tests. three.js (0.180.0) and Spark (`@sparkjsdev/spark` 2.4.0, the splat renderer) load from a CDN through an import map in `index.html`.

The same content exists in three places. Keep them in sync when journey content changes:
- `js/world.js` (`TEXT_LINES`, `MILESTONES` incl. each `panel` (a `panel.portal` = `{ href, label, title, preload }` opens an app from `apps/`; also in `catalog`, `index.html` hidden links, `sitemap.xml`, `llms.txt`), `LANDING_LINES`, `CONTACT_EMAIL`) — what the WebGL journey shows. Rock labels and panel text both come from `MILESTONES`. Panels stay short (nobody reads long text in the journey): title + subtitle/dates + at most 2 items of about 12 words, the strongest fact first. The detail lives in `resume.html`; the panel `more` link points to its section (`resume.html#<id>`: `giraffe360`, `influence-accumulation`, `ground-truth`, `splat-viewer`, `mcp-server`, `tour-narration`, `rtu`, `rvkg`, `flow`) or to the repo/post.
- `index.html` — the SEO mirror: meta/OG tags, JSON-LD, a `visually-hidden` content block, a `<noscript>` fallback.
- `resume.html` (+ `css/resume.css`) — the plain-HTML resume, linked from the page. Closed `<details>` hold the extra detail; all text is in the HTML. Its JSON-LD (`ProfilePage`) shares the Person `@id` with `index.html`.
- `resume.md`, `resume.json` (JSON Resume), `resume.pdf`, `resume-dark.pdf` — machine and print copies of the resume. `llms.txt` indexes them (update only if URLs change). Dates are year-only where the month is unknown; add months in `resume.html`, its JSON-LD, `resume.md`, `resume.json` and `js/world.js`.
- Regenerate both PDFs after any `resume.html` change: serve the site, then `google-chrome --headless=new --no-pdf-header-footer --print-to-pdf=resume.pdf "http://localhost:PORT/resume.html?expand=1"` and `google-chrome --headless=new --no-pdf-header-footer --print-to-pdf=resume-dark.pdf "http://localhost:PORT/resume.html?expand=1&print=dark"`. Each must stay 2 pages. The page offers the PDF that matches the visitor's colour scheme. Ctrl+P keeps the white print style.

- Dev URL params (read in `orchestrator.init`): `?stop=N` lands the comet at `stops[N]` at once. `?leg=N` starts the flight into stop N (N >= 1), so you can check a galaxy fly-by. Stop indexes: 0 is the trait text, 1 the Giraffe360 rock, 2-7 the apartment object stops (`splatting` cherry, `windows-mirrors` vase, `benchmarking` GPU, `mesh-generation` chair, `task-board-mcp` board, `tour-narration` robot), 8-10 the education rocks (`rvkg`, `ai-talent`, `rtu`), 11-13 the project stops (FLOW, CALCULATOR, SORTING), 14 the landing. `?leg=1` checks the first galaxy fly-by, `?leg=2` the dive into the apartment (with a galaxy), `?leg=3`..`?leg=7` the indoor flights (doorways), `?leg=8` the exit over the window wall to the first education rock, `?leg=9`/`?leg=10` the rock hops, `?leg=11` the warp into the tunnel, `?leg=12`/`?leg=13` the tunnel hops (with a fly-by each), `?leg=14` the warp out and the roof dive. `?go=<id>` lands at a stop by id (`&mode=fly` arrives by flight, like `?leg`; unknown id gives the normal intro). `?t=S` steps S seconds before the first frame (dev only; combine with `?stop`/`?leg`). `?freeze` (with `?t=S`) keeps showing that state, so headless screenshots show exactly the time asked for. `?explore=1` (with `?go=<apartment stop or contact>`) starts in walk mode; `window.__walk` (walk.js) has dev helpers (`state`, `setPose`, `walkTo`, `simulate(s, dt)` with a fixed dt, `screenOf`, `lookAt`, `onTap`).
- Headless Chrome (SwiftShader) runs almost no animation frames. `?stop=N` works headless because it needs no frames to settle. `?leg=N` fly-bys need a real browser.
- Camera smoothness check (dev only). Start the server, then run `python3 analysis/camera_smoothness.py OUT_DIR --label NAME`. It runs `dev/camlog.html` in headless Chrome. The page plays the whole journey offline with a fixed dt and auto-taps. It needs no GPU frames. The script runs four dt profiles (30, 60, 144 fps, and a jittery dt). It saves the logs and one graph per profile in OUT_DIR, and prints the spikes over each limit (limits are in the script header). New flights must show 0 spikes at all profiles (the open-space rock legs with a galaxy fly-by and the landing departure show a few small ones; main has the same kind). Tunnel flights (frames logged with `tunnel: 1`) have their own speed, acceleration and jerk limits (`TUNNEL_LIMITS`: the tunnel runs at 2x pace, so acceleration grows 4x); rotation limits are the same everywhere. Use `--dt 60` for one profile, `--url` for another server, and `--compare A B` to draw two saved labels over each other. The route is seeded (`?seed=N` on the page), so runs before and after a change are comparable.
- `?portal=1` lands at the first stop with a portal (or the `?go`/`?stop` stop) and enters it after the view delay; with it, `?t=S` counts from the portal start (`?portal=1&t=0.8&freeze` shows the flash, `&t=2.5` the open overlay). The smoothness check takes a portal step with `--params dim=1` (camlog.html `dim=S`: enter the first portal, stay S s, come back). In camlog.html three.js object ids (`generateUUID`) use their own random stream, so a new mesh does not change the seeded route; compare against a base run made with the same camlog.html.
- `analysis/attractor_chaos_analysis.py` is an offline helper used to derive attractor `scale`/`center` constants. It is not part of the site.

## Architecture

Everything renders into one canvas (`#attractor`). The core idea: **one continuous trail line travels through world space for the whole experience**. The comet streak, traced text, rock outlines, flight arcs, and attractor curves are all points pushed into the same ring buffer. The world is built once at start and is static. Each stop sits at a fixed random position in 3D space.

### Module roles (js/)

- **main.js** — bootstrap and input. The rAF loop calls `orchestrator.update(dt)`. A pointer that moves less than 10px is a tap and calls `onTap()`. Enter and Space (outside `a`/`button`) also count as a tap. Pointer events inside `OVERLAYS` (`.site-nav`, `.stop-panel`, `.dimension`, `.room-tools`, `.walk-ui`, `.intro-links`) are ignored. The intro's "skip to work" is a real `?go=<first rnd stop>&mode=fly` link (the orchestrator sets it); main.js turns its click into `journey.goTo(id, { mode: 'fly' })`; the links hide with the first tap prompt and never come back. It routes all input by `inputOwner()` (input.js): `portal` (a project app opens, is open or closes: no pointer or key input), `walk` (drag looks, tap walks or picks, WASD/arrows walk, Enter/Space do nothing), `tool` (taps belong to depthTool.js), `journey`. Hover (cursor, rim) is live only for `journey`; any other owner clears it. Esc: dimension.js closes the app first (`preventDefault`); depthTool.js turns its tools off only when the event is not handled; walk mode ignores Esc (it has its Back button). It raycasts the 3D LinkedIn and GitHub icons, the landing's mail plane and the portal rim (`getPortalHit`: hover sorts the rim, `setPortalHover`; a tap calls `enterPortal()`) for clicks and cursor. An IntersectionObserver pauses rendering when the canvas is offscreen.
- **input.js** — one input owner (`inputOwner()`: `journey` | `portal` | `walk` | `tool`). The orchestrator sets the owner of its phase (`setPhase`: PORTAL_IN/DIMENSION/PORTAL_OUT → `portal`, EXPLORE → `walk`); depthTool.js calls `setToolOn`. A tool wins over the journey and walk mode, not over a portal. It mirrors the owner to `body[data-input]` for CSS.
- **world.js** — builds the static world once (`buildWorld(scene)`). `ROUTE` lists the stops in order: one TEXT block, the Giraffe360 ROCK (universe `work`), six OBJECTs (universe `rnd`), three education ROCKs (universe `education`), three PROJECTs, LANDING. The rocks after the apartment are placed once the apartment and the tunnel exist (`placeAfterApartment`, `AFTER_TRIES`): clear of the whole tunnel axis (`TUNNEL_CLEAR`) and the apartment, and the last one is the try whose line to the throat best follows the tunnel axis there (no hairpin into the warp). `FLYBYS` lists the fly-by projects (`milestone`, `before`: the project stop they hang in front of, `title` and `skills`: the two text lines under the viz, so a reader sees what each project is and shows); they have no stop and no panel, but keep their `MILESTONES` entry. **Apartment**: one rigid frame (`apartment`: position, quaternion, scale; `roomToWorld`/`worldToRoom`), placed with the first OBJECT by `placeApartmentAndTunnel`: the window sits `APARTMENT_HOP` from the Giraffe360 rock (a little lower, `APARTMENT_DROP`), facing 90° ± `WINDOW_YAW_SPREAD` off the way back; the tunnel leaves the window along `winDir` (dipping `EXIT_DIVE`); candidates must keep the rocks `MIN_SEPARATION` from the apartment and `TUNNEL_CLEAR` from the tunnel axis, and the apartment `TUNNEL_CLEAR` from the axis except the last `TUNNEL_EXIT_FREE`. Room units (the .sog frame): +Y up, 1 unit = 3.63 m, floor `ROOM_FLOOR`, ceiling cut at y 0.30, bay windows on −Z, `ROOM_BOX` holds all rooms. The scale is the landing fit / (`LANDING_CAM_Z` − `LANDING_TEXT.z`), computed once at build. OBJECT stops (`buildObjectStop`): `OBJECT_SPOTS` (base x/z, `y` = the real surface it stands on (coffee table, dining table, desk; default the floor), `scale` = real size (cherry 17 cm, GPU 30 cm, vase 35 cm, robot 30 cm, chair 91 cm, wall board 1 m), the VIEW camera spot `cam` (the wall board's lies on the wall normal), `fitMax` so the camera stays inside the walls, `doors` from the previous object, `light` = brightness factor for the spot, `haloTilt`), `OBJECT_SIZE` (`bottom`: where the content starts, the board's panel), `HALO_R`; check every new spot in the splat (contact with the surface, no intersection, measure surface heights and wall planes from the PLY); the stroke set is a halo ring (`HALO_TILT`, `HALO_POINTS`; the wall board's ring lies in its plane), a subtle accent (`HALO_INTENSITY` under the bloom threshold), dim (`HALO_DIM_ALPHA`) until traced; `stop.normal` is the view direction, `stop.up` the ring's second axis. Apartment strokes (halo rings, the landing text) have their own material and show only for the focused stop (`setHaloFocus`, `HALO_FADE_TIME`): they have no depth test and would shine through walls. `viasFor(from, dest)` gives a flight's via points `{ p, dir? }`: in over the cut ceiling (`ENTRY_*`, `WINDOW_STANDOFF`), through `DOORS` (three vias in a line, `DOOR_LEAD`; `LW1`/`LW2` are single vias of a lane round the living-room sofa, which sits just inside the LH door), out over the window wall (`WALL_TOP`/`WALL_OUT`), and over the roof (`ROOM_ROOF`) to the landing. `isIndoorFlight` = object to object. `setRoomFade` (room.js) fades the outside world's lines indoors. The tunnel axis starts at the window (`TUNNEL_HOP` out). Layout along s: the warp throat at 0, a rush, the first fly-by at `TUNNEL_RUSH`, then stop, fly-by, stop … each `FLYBY_GAP` apart, then `TUNNEL_EXIT_AFTER` to the exit. The middle of every stretch is a fast zone (`tunnel.setZones`, ramps `FAST_ZONE_RAMP`, margins `FAST_ZONE_MARGIN` from the throat / stops and fly-bys / exit). Project stops sit on the centreline and face along the tunnel. Each carries `tunnelS` and `viz` (projectViz.js); its `points2d` start at the viz centre (the comet flies into the centre), run out to a rounded frame round the viz (traced by the comet only), then the label under it (static strokes). Fly-bys sit `FLYBY_SIDE` beside the axis (left, right, left), facing the approaching comet; each `flybys[]` entry carries `offset`, `center` and `radius` for the comet's spiral. The landing sits in the living room (`LANDING_TEXT`, facing the windows); `buildWorld` warns if the tunnel exit is not `LANDING_EXIT_DIST` from the landing camera. `setInsideFade(f)` (0 outside .. 1 inside) cross-fades the two worlds: the outside lines (galaxies, rocks, text, landing) and the tunnel's project labels have their own shared stop material (`uVis`), and the vizzes fade with it. The text starts dim (`TEXT_DIM_ALPHA`), and `lightStop(stop, idx)` brightens it as the comet traces it. Each planar stop also carries `blockMid`/`blockHalfH` (the real vertical middle and half-height of its strokes). Each `StopType` (`TEXT`, `ROCK`, `LANDING`, `PROJECT`, `OBJECT`) has a pre-built point set with baked HDR colors and one shared stop shader. Stops scatter randomly: each hop is a random direction, lightly biased along `journeyDir`, with min/max hop and separation limits (rocks are one scene, but still about 35 units apart so each flight takes about 5 s). Each rock stop carries `panel` from `MILESTONES` (`{ title, subtitle?, dates?, items: [{ text, href? }], more?: { href, label } }`). `ATTRACTORS` are no longer stops: `buildWorld` also builds `scenery[]`, one dim curve per flight leg (`SCENERY_LEGS`, filled from `ROUTE`: each leg into a rock and the dive into the first object; none indoors, on the warp in, inside the tunnel or on the roof dive; kept clear of the tube and the apartment; attractor `k % ATTRACTORS.length`), placed beside the leg. `updateWorld(dt, headS)` spins them, moves the tunnel, and updates only the visualizations near the viewer's arc parameter `headS` (`VIZ_RANGE`). Exports `stops[]`, `scenery[]`, `flybys[]`, `tunnelExitS`, `apartment`, `roomToWorld`, `worldToRoom`, `fitDistance` (shared camera fit), `viasFor`, `isIndoorFlight`, `updateWorld`, `setInsideFade`/`getInsideFade`, `setRoomFade`, `setHaloFocus`, `planePointToWorld`, `CONTACT_EMAIL`, and `getMailPlane()`. The mail plane is an invisible mesh over the email line of the landing; main.js raycasts it for a `mailto:` click.
- **orchestrator.js** — the brain. A `Phase` state machine: INTRO → ROCKET_EXIT (first tap: the rocket morphs into the comet in place) → TRAVEL → VIEW, then back to TRAVEL on the next tap. At a stop with a portal (`stop.portal` = `panel.portal`): VIEW → PORTAL_IN → DIMENSION → PORTAL_OUT → VIEW. `enterPortal(byButton)` (a rim hit waits for `VIEW_TAP_DELAY`, the panel button does not; DOM event `journey:portal-request`): `emitStop('leave')`, event `journey:portal` `enter`; the comet flies a Bezier through the viz centre to `PORTAL_DEPTH` behind it, the camera dollies on a rail (`cam.setRail`, smootherstep over `PORTAL_TIME`) through the viz plane, and the warp flash rises (`setBloomBoost`, `WARP_FOV`, streaks, rush, comet intensity; peak at `PORTAL_PEAK`); at strength `PORTAL_SHOW` it sends `show` (the overlay fades in). DIMENSION: `update` returns at once (no render, the main loop idles). `exitPortal()` (event `journey:portal-exit`, also from PORTAL_IN) flies the same way back, the flash falls over `PORTAL_FALL`, then `enterView()` (re-trace from the viz centre, panel back, view delay again). Reduced motion: no flight, the overlay fades (`PORTAL_FADE`). The rim's prefetch progress comes in as `journey:portal-progress`. A portal stop's fit takes in the rim (`stop.fitHalfW/H`) and its loop circles the rim (`rimLoopPos`). VIEW ⇄ EXPLORE (walk mode, walk.js) at apartment stops and the landing: `enterExplore` hides the trail and the halo focus, disables OrbitControls, clears the screen shift, and sends `journey:explore` `{ phase: 'enter' }` (depthTool.js shows its toolbar; `leave` on the way out); `update` then runs `walk.update` and skips `updateView` and `cam.update`; `stopIndex` does not change. `exitExplore` ("Back to the journey") eases to the VIEW pose and calls `enterView()`; `jumpTo`/`setupTravel` leave EXPLORE at once (`leaveExploreNow`). A portal opens only from VIEW, so never from walk mode. Taps do not queue across phases, and each stop has a minimum view time (`VIEW_TAP_DELAY`). A flight is `travelLegs`: chained cubic Beziers, with an optional via-point and a corkscrew on the first flight. The path is walked by arc length (`travelArc`), so the speed does not jump where legs join. The camera follows `cameraAnchor`, the path averaged over ±`CAM_PATH_WINDOW` s, so tight bends do not whip it. Stops depart along their loop motion (`HOVER_LOOKAHEAD`). If a scenery galaxy sits near the flight line, `pickViaScenery` adds a via-point so the comet swings past it (open-space flights only). Flights that touch the tunnel (`buildTunnelLegs`) use a second leg kind, `{ tunnel: true, s0, s1, endOffset }`: the comet flies the tunnel centreline itself, and the last `TUNNEL_LAND` units blend onto the destination's first stroke point. A departure joins the centreline with `joinLeg` (tangent-continuous, aimed mostly at the join point, `JOIN_HEADING_MIX`). If a fly-by lies on the hop (`pushCentre`), a third leg kind, `{ helix: true, s0, s1, R, offset }`, spirals round it: the comet leaves the centreline (radius and offset ramp in with smootherstep), makes `FLYBY_TURNS` round the viz, and rejoins. Pacing: every tunnel timing (pace, eases, arrival blend, warp) is scaled by `TUNNEL_TIME_SCALE` (0.5 = 2x speed over the same layout). Tunnel flights cruise (ease in/out over `TUNNEL_EASE_TIME`, pace `TUNNEL_SPEED`), and `buildArcTable` weights the tunnel legs (`tunnelWeight`): light in the fast zones (speed × `TUNNEL_FAST` at a zone's flat top), heavy round a fly-by (`FLYBY_SLOW` over `FLYBY_SLOW_H`) and heavier still on the spiral (`FLYBY_SPIRAL_W`, timed by the centreline under it, so the comet's s progresses smoothly). All C2, so speed, acceleration and jerk stay bounded; peak ~75 u/s. At peak speed the rush adds gentle streaks, ring pulses and `RUSH_FOV`. `travelS` gives the comet's smooth s from the legs. Round a fly-by the camera frames the viz (`flybyFraming`, a C2 bump over `FLYBY_CAM_L`): the anchor rides the centreline, hangs back by up to `FLYBY_CAM_LAG` (a slow dolly-in) and slides onto the viz axis, the heading turns to the tunnel tangent, the chase distance goes to `FLYBY_CAM_DIST` (must stay under `controls.maxDistance` or OrbitControls clamps and kinks the path); the panel shift comes back after it. Warp in = the last education rock → tunnel start → first project (the apartment exit is a flight out over the window wall to the first education rock, `exitTowards`); warp out = last project → tunnel exit → over the roof (via) → dive to the landing. Via points (`viasFor`) chain through `buildViaLegs` (with `dir` the comet crosses the via exactly along it, `VIA_PULL`); leaving an object the comet first climbs over it (`LIFT`, `LIFT_AHEAD`; skipped when the next via is `LIFT_SKIP` higher anyway), and it arrives face-on (the last via `APPROACH_FIT`/`APPROACH_FIT_INDOOR` × fit in front). **Indoor flights** (object to object): pace `INDOOR_SPEED` in room units (`INDOOR_MIN`/`INDOOR_MAX`), and the camera rides a rail instead of the chase camera (`cam.setRail`): it sits on the comet's own path `RAIL_BACK` behind and `RAIL_UP` above it (the path averaged over ±`RAIL_WINDOW`), so it passes the doorways where the comet does. The rail heading is a yaw and a pitch spring with a speed cap (`RAIL_TURN_TIME`, `RAIL_TURN_MAX`, pitch within `RAIL_MAX_PITCH`), starting at the departure view; a flight lasts at least its total view turn (`railTurn`) at `RAIL_TURN_SHARE` of that cap. The camera eases from the departure pose onto the rail over `railIn` (`RAIL_IN`, `RAIL_IN_RATE`), keeps clear of the object it left (`RAIL_CLEAR`, a smooth radial push), and blends into the VIEW pose over the last `ARRIVE_BLEND`; a light spring (`RAIL_FILTER`) filters the position. The warp (`updateWarp`) is a wormhole, all cross-fades and no cuts: both tunnel ends are flared mouths (tunnel.js). Warp in: from `WARP_FADE_PRE` s before the throat the funnel of the tunnel's own rings and strands fades in ahead and swirls, while the outside world fades out (`setInsideFade`); around the throat a time bump (`WARP_RISE`/`WARP_FALL`) adds star streaks, a gentle FOV kick (`WARP_FOV`), bloom (`setBloomBoost`) and a brighter comet; the walls narrow into the tunnel. Warp out is the reverse: the end flares open behind the comet, and the landing world fades back in. The far intro objects switch at the middle of the fade (`intro.setIntroVisible`). Each frame `headS` (the comet's arc parameter, or the stop's in VIEW) moves the tunnel window. The chase distance eases from the departure distance to the destination fit over the first `FOLLOW_EASE` of the path. Arrival: over the last `ARRIVE_BLEND` of the flight time (tunnel stops: the last `ARRIVE_TIME` s; only when the flight arrives from the front, `ARRIVE_MIN_DOT`) the chase pose blends into the stop's VIEW pose (`cam.setArrival`: look at the stop centre, camera at the face-on spot), so the focus never jumps from the comet to the stop; departures keep the two-spring hand-off in camera.js. Project stops: the comet loops round the viz frame (`frameLoopPos`), no auto-rotate. Object stops: the comet traces the halo ring (`OBJECT_TRACE_DURATION`, lighting it), then rides it (`ringLoopPos`, easing to `OBJECT_LOOP_PERIOD`), no auto-rotate; the fit is capped at `stop.fitMax`. `emitStop('enter')` runs at the end of `enterView`. `emitStop('leave')` runs at the start of `setupTravel`. For stops with a panel (`hasPanel`: rocks, objects and projects), `setupTravel` calls `cam.setScreenShift(true)`, and the fit distance leaves room for the panel (`ROCK_FIT_SIDE`, `ROCK_FIT_BOTTOM`). It owns `worldPos`, the world-space comet head that the camera follows. In VIEW, planar stops first trace their strokes once (`tracing`), then loop (`loopT`). The TEXT stop is special: faster trace (`TEXT_TRACE_DURATION`), the loop is a helix (`helixPos`, `SPIRAL_*`), and after `SPIRAL_DURATION` it calls `setupTravel` itself — no tap. After the landing the tour loops back to stop 1 (the Giraffe360 rock). A tap in VIEW waits for the view delay and for the face-on glide to settle (`camAligned`): an arrival from behind (the loop back) glides round the stop, and a departure mid-glide would reverse that turn in a snap.
- **portal.js** — the portal flight (VIEW → PORTAL_IN → DIMENSION → PORTAL_OUT → VIEW; see orchestrator.js above for the behaviour): `enterPortal`, `exitPortal`, `getPortalHit`, `setPortalHover`, `update(dt, goingIn)`, the `PORTAL_*` tuning and the `journey:portal-*` listeners. The orchestrator owns the phase and passes a small interface `J` at init (phase, stop, comet state, `enterPhase`, `enterView`, `fitFor`, …).
- **explore.js** — VIEW ⇄ EXPLORE for the orchestrator (`enterExplore`, `exitExplore`, `leaveNow`, `update`), with the same `J`. walk.js registers itself (`registerWalker`); main.js imports walk.js, `dev/camlog.html` does not, so the harness has no walk mode.
- **walk.js** — walk + collect mode in the apartment (Phase.EXPLORE). Self-contained: it lazily loads `assets/room/walk.json` (when an apartment stop or the landing is entered) and owns the camera pose while walking (`roomToWorld` + `apartment.quaternion` from room.js; no camera.js changes). It registers `{ canWalk, enterWalk, exitWalk(viewPos, viewTarget, fov, done), update(dt) }` with explore.js; its buttons call `enterExplore`/`exitExplore`. Input from main.js: `onTap`, `onDrag`, `setKeys` (Enter/Space do nothing in walk mode). Walker (ported from the W0 spike): A* on the grid (wall cost `WALL_SOFT`/`WALL_COST`), line-of-sight string pulling, look-ahead carrot, a 2 cm collision skin with true sliding (the 0.2 m body radius is baked into the grid), gentle wall avoidance from the clearance map (`AVOID_*`), velocity and look springs. Eye 1.55 m, `FOV` 70° vertical, pitch −60..+15° (the ceiling is a void above ~2.2 m). Drag look is direct; only auto turns (path heading, turn-to-object) are capped (`YAW_MAX`). Artifacts: a tap ray hits an invisible sphere per object stop (needs a line of sight on the grid's `sight` bits): turn to it, its panel (`walk:panel` event → stopPanel.js) and a Collect button; collected ids in `localStorage['rnd.collected']` (try/catch); halos (own lines, no depth test, faded by line of sight): dim hint until collected, lit after; HUD `.walk-hud` (back button, "n / 6") under the nav; all collected → "You found all six" panel with the resume link. DOM: `.walk-explore` in `.stop-panel-actions` (apartment stops) and `.walk-explore-float` (the landing), `.walk-collect`, `.walk-hud`. Grid: `~/work/zipnerf-room/scripts/make_walk_grid.py` (opacity > 0.3 in the body band, 5 cm cells, dilate 0.2 m, flood fill from the living room; `--fog`: cells with low-opacity haze near eye height are not walkable; `sight` bits: walls at eye height; it checks the four doorway routes, `--fogsweep` compares fog limits). Copy its `web/walk.json` to `assets/room/walk.json`.
- **tunnel.js** — the projects tunnel. The centreline is analytic (`setFrame(origin, axis, turn, length)`): a base axis that is a wide circular arc turning by `TUNNEL_TURN` (2π − 0.5, almost a full circle) over the tunnel length, so the exit comes back behind the apartment it left (the start and the exit lie close: set `setUnwrapRef(0)` before a flight into the tunnel start, so `sOf` unwraps the right way), plus a sideways / up snake, sums of sines (`AMP`, `PERIOD`, random phases). In the fast zones (`setZones`, flat tops with smootherstep ramps) the snake flattens to `FAST_STRAIGHT`, so the path is nearly straight where the comet rushes; `fastness(s)` (0..1) drives the speed and the rush effects. JS mirrors: `centreWorld`, `tangentWorld`, `frameWorld`, `sOf` (arc parameter of a point, unwrapped round the arc), `axisDistance` (placement). The wall is GPU-only: helical strands (`STRANDS`: pitch, handedness, colour) and beaded rings, re-sampled every frame in the vertex shader in a window round the viewer (`setView(s)`, `WINDOW_BACK`/`WINDOW_AHEAD`), so it never ends and no buffer changes. Time motion (all GPU, accumulators in `update(dt)`): each stretch spins back and forth with its own phase (bounded twist), pulses run forward, the radius breathes, and the far tunnel snakes (zero within `WOBBLE_NEAR` of the viewer, so the comet path is static). `TUNNEL_RADIUS` 4.5 keeps the chase camera inside. Wormhole mouths: past `setFlare(sIn, sOut)` the radius grows as e^(d / `FLARE_LENGTH`) (capped, dimmed by `FLARE_ALPHA`) and the mouth swirls (`setVortex(t)`, zero inside the tunnel so the twist stays bounded). Warp controls: `setFade`, `setRush`, `setVortex`, and the star streaks (`updateStreaks`). It does not touch the DOM.
- **projectViz.js** — `buildProjectViz(label, { title, skills, portal })` → `{ group, halfW, halfH, update(dt), rim }`. With `portal` (SORTING only for now) `portalRim` adds the rim: `RIM_N` radial ticks on a circle (`RIM_R0`) just outside the corner brackets, a shuffled array that sorts itself while hovered (quick sort ops) and shuffles again after (`RIM_RESHUFFLE`); the lit share is the app's loading progress (`setProgress`); `rim.hit` is an invisible ring mesh (`RIM_HIT`, a tap on the viz itself still advances); its own random numbers (`rimRandom`). Each viz: one live animation per project in a local plane (x right, y up, z to the camera; content within `HALF_W` × `HALF_H`), dim corner brackets as the shared frame. SORTING (the showpiece): real algorithms replayed from recorded compare/swap/write ops, five layouts from the original project (columns, circle, points, spiral, pyramid) morphing between runs. CALCULATOR: grid, three functions plotted by a glowing pen, roots light up. FLOW: rest timer, weekly volume bars, ACWR load lines. Fly-bys: MONTE CARLO (GBM price paths growing on the GPU, a log-normal histogram filling), BALANCER (consistent-hashing ring, requests, failing servers), NEAT (evolving network with flowing signals). Soft ribbons (`ribbon`) for curves that must read well; counts scale with `isMobile`. A short prewarm means no viz starts empty. It does not touch the DOM.
- **attractors.js** — three.js toolkit: scene, camera, renderer, UnrealBloom composer (`setBloomBoost(w)` for the warp), OrbitControls, the `ATTRACTORS` table (derivatives, `dt`, `scale`, `center`, palette; used for palettes and scenery curves), the RK4 integrator, the trail system, and the starfield. The trail is one `THREE.Line` with position/alpha/color attributes (`MAX_POINTS` ring buffer, additive blending). `pushPointWorld` pushes world-space coords into the trail.
- **camera.js** — two modes: `Mode.ORBIT` (target eases to a fixed center, auto-rotate) and `Mode.FOLLOW` (chase camera: `camera = look − chaseDir×dist + up×FOLLOW_UP·dist`, `look = comet + chaseDir×FOLLOW_AHEAD·dist`; `setFollowDistance` is set per flight to the destination's fit distance; the distance spring has a speed cap, `DIST_MAX_SPEED`). All easing uses critically damped springs (`smoothDampScalar`/`smoothDampVec`), so speeds never jump. The chase heading is a yaw and a pitch spring with a speed cap (`TURN_*`), and its pitch stays within `MAX_CHASE_PITCH`, so the view does not spin near the poles. A switch to FOLLOW keeps the current pose and velocity and blends the difference out (`HANDOFF_TIME`; two springs in a row, so the blend starts without a jolt). ORBIT eases the target with `ORBIT_TIME` and keeps its arrival velocity. `setScreenShift(on, immediate)` eases a `camera.setViewOffset` projection shift (two springs in a row, so it starts with zero acceleration): the rock moves to the left (side layout) or the top (bottom layout). The orbit target does not move. `isPanelSideLayout()` uses `PANEL_SIDE_QUERY`.
- **agentApi.js** — self-initialising. It sets `window.journey` (listUniverses, listStops, getStop, current, goTo, next, previous, whenIdle, resumeLinks) and registers 7 WebMCP tools when `document.modelContext ?? navigator.modelContext` exists (no polyfill). It reads the static `catalog` of world.js (works before `buildWorld`) and navigates only through orchestrator `jumpTo`/`setupTravel`/`onTap`, never the camera. `goTo` (and next/previous) refuses during TRAVEL (`travelling`), while a project app is open or opening (`in-portal`), in walk mode (`exploring`), and for fly-bys (`not-navigable`). Keep `llms.txt` (Journey section, `?go` links) in sync with the ids.
- **dimension.js** — self-initialising (loaded after `stopPanel.js`, before `main.js`). The `.dimension` overlay in `index.html`: a bar (back button, title, new tab link) and an iframe with the app (`panel.portal.href` + `?embed=1`). On `journey:stop` enter with a portal it prefetches `panel.portal.preload` (fills the HTTP cache) and reports the progress (`journey:portal-progress`). `journey:portal` `enter` loads the iframe and adds a history entry; `show` fades it in (`FADE_MS`, same as the CSS) and focuses the app. Close: the back button, Esc, the app's `postMessage({ type: 'journey:exit' })` (same origin) and browser Back all go through history (`history.back()` → `popstate` → close), then `journey:portal-exit`; after the fade the iframe unloads.
- **apps/** — standalone project apps (`/apps/<id>/index.html`), shown by dimension.js in the overlay and linked as plain pages (SEO, accessible fallback, a new tab). `?embed=1` hides the app's own header; its Esc at the menu posts `journey:exit`. `apps/sorting/`: sort_visualization. `wasm/sortvis.js` + `.wasm` are built from the sort_visualization repo (`build_web.sh`, `web/shim.cpp`: the original SortAlgorithms.cpp and ShuffleAlgorithms.cpp, a glibc-compatible `rand`, `drawing()` records a step log) and vendored here; `worker.js` runs them in a Web Worker and returns the log; `drawer.js` is a JavaScript port of ArrayDrawer.cpp (columns, points, circle, spiral, pyramid; the original themes, 1000 × 1000 units); `app.js` is the Main.cpp flow (menu, shuffle, sort, 2 s pauses), speed keys (Right/D, Left/A, Esc) and buttons. Dev params: `?seed`, `?theme`, `?layout`, `?sort`, `?autorun`. New portal files go into `panel.portal.preload`.
- **stopPanel.js** — self-initialising module. It listens for the `journey:stop` event on `window` and fills the `.stop-panel` element with `textContent` only (no `innerHTML`). A `panel.portal` shows the `.stop-panel-portal` link (a real link to the app; a plain click sends `journey:portal-request`). `enter` with a panel shows it (adds `.visible` and `body.panel-open`). `leave`, or `enter` without a panel, hides it. Contract: `detail = { phase: 'enter' | 'leave', index, type, panel }`. You can test it from the console by dispatching that event.
- **room.js** — self-initialising module (loaded after `stopPanel.js`). It renders the apartment: a Gaussian splat of a real flat (Zip-NeRF "london" scene, CC BY 4.0, reconstructed with gsplat) and the six splat objects, into the frame that world.js placed (`apartment`; it never places anything itself). Assets: `assets/room/apartment.sog` (10.9 MB) and `apartment-lite.sog` (5.7 MB, used when `isMobile`). Spark and objects.js load lazily (one dynamic import; objects.js imports Spark statically) when the comet enters a stop outside `NO_PREFETCH_UNIVERSES` (`intro`): the traits do not load it, the Giraffe360 rock (and any `?go` stop) does. By universe, never by index. Opacity follows the camera's distance outside `apartment.box` in room units (`FADE_START`/`FADE_FULL`, dt-independent; it reads as a dollhouse from outside, the ceiling is cut), times `1 − getInsideFade()` (hidden inside the tunnel). Indoors (`INDOOR_FADE`) it fades the outside world's lines (`setRoomFade`), the stars and the intro objects. `ROOM_BRIGHTNESS` dims the room so the glowing strokes read; `OBJECT_LIGHT` (warm, dim, × each spot's `light`) makes the baked-white objects match the lamp-lit room, `BLOOM_THRESHOLD_IN_ROOM` keeps them from blooming, `OBJECT_SPLATS` per object. The SparkRenderer has `renderOrder -10`, so the additive strokes and trail draw over the splats. It toggles `.room-credit` (apartment stops and the landing; CSS hides it over the bottom panel, and in the side layout lifts the tap prompt above it). It exports `roomMesh` (null until loaded), `objectMeshes` and `ROOM_BRIGHTNESS`, and re-exports the apartment API of world.js (`apartment`, `roomToWorld`, `worldToRoom`, `M_PER_UNIT`): walk.js and depthTool.js read the apartment from room.js only. `dev/camlog.html` does not load it.
- **depthTool.js** — self-initialising module (loaded after `room.js`). The `.room-tools` toolbar (Depth, Measure; hint "Try the depth lens") lives in walk mode only: `journey:explore` `enter` shows it, `leave` turns the tools off and hides it (the stop panel offers one action, "Explore the flat"). Its buttons stay disabled until a raycast probe hits the splat (Spark raycast is empty until frames render). Depth: a Spark `worldModifier` dyno block, attached to the room and object meshes on first use (`updateGenerator`), recolours splats inside a cone round the pointer ray (`LENS_TAN`) by camera distance on a log scale (`LENS_NEAR_M` 0.5 .. `LENS_FAR_M` 6 m) through `RAMP` (part of "inferno": bright near, dark far), times `LENS_GAIN` (under the bloom threshold); a legend (`.room-tools-legend`, near · ramp · far in metres) shows while it is on; uniforms change → `updateVersion()`. The lens is passive: taps still walk. Measure: a click (not a drag) raycasts (`minRaycastOpacity` 0.3, on click only), two points give a line, dots and "≈ x.xx m" (cm below 1 m): world distance / `apartment.scale` × `M_PER_UNIT` (world.js, 3.45, approximately metric ±3 %). While measuring, `setToolOn` (input.js) gives it the taps; a drag still looks round and WASD still walks. Phones (`isMobile` or a coarse pointer): lens and picks on the screen centre (`.room-tools-cross`), a Mark button picks. Esc turns the tools off. It reads the apartment (`apartment`, `M_PER_UNIT`, the meshes) from room.js only.
- **objects.js** — procedural Gaussian-splat objects (`buildObject(name, { count, rng })` → a Spark `SplatMesh` about 1 unit tall, base at the origin, front +Z; `userData.idle(t)` animates it): cherry (splatting), vase (windows and mirrors: a clean half and a noisy half), gpu (benchmarking), chair (meshes: a triangle-mesh wireframe, half filled with splats), board (task board, wall-mounted: no easel, no shadow), robot (narration). Only the robot turns a little and the GPU fans spin; the rest stand still on their surfaces. Baked lighting (splats are unlit), `contactShadow`, `FOOT` sizes, `mulberry32`. Loaded only by room.js.
- **intro3d.js** — the 3D intro: extruded name text, LinkedIn and GitHub icons (side by side, with `LINKEDIN_URL`/`GITHUB_URL`), and the rocket with idle loops. Objects live on a world-space anchor, so view rotation moves them with the stars. On the first tap the text and icons stay put. Only the rocket animates: `setRocketCharging` freezes its idle transform and stretches it into the comet streak. `getRocketTipWorld`/`getRocketDirWorld` give the orchestrator the start point and heading.
- **strokeFont.js** — single-stroke vector font and procedural rock outlines (`generateTextLines`, `generateRockWithLabel`). The rock label is capped at 80% of the rock width. They return flat 2D point arrays `{x, y, c}`. `c=0` is a faint pen-travel stroke. `c=1` is a letter stroke. world.js maps them onto a world-space plane.

### Conventions that matter

- **Ids, not indexes**: every stop and fly-by has a stable `id` and a `universe` in world.js (`ROUTE`, `FLYBYS`, `UNIVERSES`). The agent API, `?go` and `llms.txt` use ids. A new universe is a new `UNIVERSES` entry plus `ROUTE` entries. `journey:stop` detail also carries `id`, `universe`, `label`.
- **Script order**: `stopPanel.js`, `room.js`, `depthTool.js`, `dimension.js`, `agentApi.js`, `main.js`. `js/agentApi.js` loads after `stopPanel.js` and before `main.js`; `depthTool.js` after `room.js`.

- **HTML overlays (`.site-nav`, `.stop-panel`, `.dimension`, `.room-tools`, `.walk-ui`, `.intro-links`)**: they sit over the canvas. main.js must keep ignoring pointer events inside them (`OVERLAYS`), or a link or button click would also advance the journey (or walk).
- **Check the apartment**: `?go=<object id>` (stops 2-7) and `?go=contact` (the landing, last stop; for now 14) show it. Splats need real frames to sort, so headless Chrome needs about 25 s. The intro and the traits must make no `.sog` request. Do not hard-code the landing or object indexes in code. Headless Chrome logs a `VALIDATE_STATUS false` shader error once Spark is in the scene (main has it too).
- **Script order**: in `index.html`, `js/stopPanel.js` must load BEFORE `js/main.js`. With `?stop=N`, `orchestrator.init` dispatches `journey:stop` synchronously. If the listener does not exist yet, the event is lost.
- **Layout query sync**: the media query `(min-width: 700px) and (orientation: landscape)` appears in `css/style.css` (panel at the side) and as `PANEL_SIDE_QUERY` in camera.js (screen shift). Change both together.
- **Brightness via intensity**: `trail.pointIntensity` > 1 writes HDR colors that feed the bloom pass (bold strokes, streak flash). A value < 1 renders faint (connector strokes). See `STROKE_INTENSITY`/`LINK_INTENSITY` in world.js and `TRACE_STROKE_INTENSITY`/`TRACE_LINK_INTENSITY` in orchestrator.js.
- **Palette switches**: set `trail.colorFreezeIdx = trail.pointCount` before changing `trail.attractorIdx`, so drawn points keep their colors.
- **Camera fights**: phases that auto-align the camera (`camAligned` + a spherical glide around the stop toward `textFacePos`) must yield to the user. A `controls` `start` listener sets `camAligned = true` when the user grabs the view. Use this pattern for any new camera steering.
- **Frame-rate independence**: drawing speeds are dt-based (`drawAcc`/`traceAcc` point budgets, sub-stepped curve sampling between `prevT` and `t`). Never use per-frame counts.
- **Starfield**: stars wrap in a cube around the scene center and are re-projected in the vertex shader onto a shell 1x to 10x the camera-to-scene distance, with zoom-relative point sizing. They must always read as far background.
- **Mobile** (`isMobile` in attractors.js): fewer trail points and stars, lower bloom resolution, capped pixel ratio. Keep new effects behind the same scaling.
- Tuning constants live in commented blocks at the top of each module (the "Tuning" section in orchestrator.js, the constants block in world.js). Adjust them there, not inline.
