# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Personal portfolio site (GitHub Pages, `ilyaeis.github.io`). It is a single-page WebGL experience: a tap-driven "journey" that flies a glowing comet trail from an intro screen through the three trait words (it traces and spirals around them, no tap), then to four milestone rocks. After the last rock it warps into an endless, snaking tunnel of glowing strands: three project stops sit on its centreline (each a live visualization), and three smaller fly-by projects hang inside it between them. It warps out to a contact landing. On the way it swings past dim, slowly spinning strange-attractor "galaxies" (scenery). At each rock and project stop the camera shifts the stop to one side, and an HTML panel shows the milestone text on the other side. No framework, no build step, no tests. three.js (0.180.0) and Spark (`@sparkjsdev/spark` 2.4.0, the splat renderer) load from a CDN through an import map in `index.html`.

The same content exists in three places. Keep them in sync when journey content changes:
- `js/world.js` (`TEXT_LINES`, `MILESTONES` incl. each `panel`, `LANDING_LINES`, `CONTACT_EMAIL`) — what the WebGL journey shows. Rock labels and panel text both come from `MILESTONES`.
- `index.html` — the SEO mirror: meta/OG tags, JSON-LD, a `visually-hidden` content block, a `<noscript>` fallback.
- `resume.html` (+ `css/resume.css`) — the plain-HTML resume, linked from the page.

## Commands

```bash
# Serve locally (any static server works; ES modules need http://, not file://)
python3 -m http.server 8000
# then open http://localhost:8000/
```

- Deployed by pushing to `main` (GitHub Pages).
- No lint/test/build tooling. Verify changes by loading the page and tapping through all stops (hard-refresh with Ctrl+F5 to bypass cached JS).
- Dev URL params (read in `orchestrator.init`): `?stop=N` lands the comet at `stops[N]` at once. `?leg=N` starts the flight into stop N (N >= 1), so you can check a galaxy fly-by. Stop indexes: 0 is the trait text, 1-4 the rocks, 5-7 the project stops (FLOW, CALCULATOR, SORTING), 8 the landing. `?leg=1` checks the first galaxy fly-by, `?leg=5` the warp into the tunnel, `?leg=6`/`?leg=7` the tunnel hops (with a fly-by each), `?leg=8` the warp out. `?t=S` steps S seconds before the first frame (dev only; combine with `?stop`/`?leg`). `?freeze` (with `?t=S`) keeps showing that state, so headless screenshots show exactly the time asked for.
- Headless Chrome (SwiftShader) runs almost no animation frames. `?stop=N` works headless because it needs no frames to settle. `?leg=N` fly-bys need a real browser.
- Camera smoothness check (dev only). Start the server, then run `python3 analysis/camera_smoothness.py OUT_DIR --label NAME`. It runs `dev/camlog.html` in headless Chrome. The page plays the whole journey offline with a fixed dt and auto-taps. It needs no GPU frames. The script runs four dt profiles (30, 60, 144 fps, and a jittery dt). It saves the logs and one graph per profile in OUT_DIR, and prints the spikes over each limit (limits are in the script header). Use `--dt 60` for one profile, `--url` for another server, and `--compare A B` to draw two saved labels over each other. The route is seeded (`?seed=N` on the page), so runs before and after a change are comparable.
- `analysis/attractor_chaos_analysis.py` is an offline helper used to derive attractor `scale`/`center` constants. It is not part of the site.

## Architecture

Everything renders into one canvas (`#attractor`). The core idea: **one continuous trail line travels through world space for the whole experience**. The comet streak, traced text, rock outlines, flight arcs, and attractor curves are all points pushed into the same ring buffer. The world is built once at start and is static. Each stop sits at a fixed random position in 3D space.

### Module roles (js/)

- **main.js** — bootstrap and input. The rAF loop calls `orchestrator.update(dt)`. A pointer that moves less than 10px is a tap and calls `onTap()`. Enter and Space (outside `a`/`button`) also count as a tap. Pointer events inside `.site-nav` are ignored. It raycasts the 3D LinkedIn and GitHub icons and the landing's mail plane for clicks and cursor. An IntersectionObserver pauses rendering when the canvas is offscreen.
- **world.js** — builds the static world once (`buildWorld(scene)`). `ROUTE` lists the stops in order: one TEXT block, four ROCKs, three PROJECTs, LANDING. `FLYBYS` lists the fly-by projects (`milestone`, `before`: the project stop they hang in front of); they have no stop and no panel, but keep their `MILESTONES` entry. The tunnel is placed with the first PROJECT (`placeTunnel`): its axis leaves GIRAFFE360 (`TUNNEL_HOP`), stays `TUNNEL_CLEAR` from all earlier stops, and prefers a direction ahead of the GIRAFFE360 view. Project stops sit on the centreline at `s = TUNNEL_FIRST + k × TUNNEL_SPACING` and face along the tunnel. Each carries `tunnelS` and `viz` (projectViz.js); its `points2d` are a rounded frame round the viz (traced by the comet only) plus the label under it (static strokes). Fly-bys hang off the axis (`FLYBY_OFFSET`, upper left/right, turned towards the approaching comet). The stop after the tunnel is placed from the exit along the exit tangent (`placeAfterTunnel`), so the warp out has no hairpin. `setOutsideVisible(v)`: outside the tunnel the projects are hidden; inside it the galaxies, rocks, text and landing are hidden (the walls are see-through). The text starts dim (`TEXT_DIM_ALPHA`), and `lightStop(stop, idx)` brightens it as the comet traces it. Each planar stop also carries `blockMid`/`blockHalfH` (the real vertical middle and half-height of its strokes). Each `StopType` (`TEXT`, `ROCK`, `LANDING`) has a pre-built point set with baked HDR colors and one shared stop shader. Stops scatter randomly: each hop is a random direction, lightly biased along `journeyDir`, with min/max hop and separation limits (rocks are one scene, but still about 35 units apart so each flight takes about 5 s). Each rock stop carries `panel` from `MILESTONES` (`{ title, subtitle?, dates?, items: [{ text, href? }], more?: { href, label } }`). `ATTRACTORS` are no longer stops: `buildWorld` also builds `scenery[]`, one dim curve per flight leg (`SCENERY_LEGS = [1, 2, 3, 4, 8]`: none on the warp in or inside the tunnel; kept clear of the tube; attractor `k % ATTRACTORS.length`), placed beside the leg. `updateWorld(dt, headS)` spins them, moves the tunnel, and updates only the visualizations near the viewer's arc parameter `headS` (`VIZ_RANGE`). Exports `stops[]`, `scenery[]`, `flybys[]`, `tunnelExitS`, `updateWorld`, `setOutsideVisible`, `planePointToWorld`, `CONTACT_EMAIL`, and `getMailPlane()`. The mail plane is an invisible mesh over the email line of the landing; main.js raycasts it for a `mailto:` click.
- **orchestrator.js** — the brain. A `Phase` state machine: INTRO → ROCKET_EXIT (first tap: the rocket morphs into the comet in place) → TRAVEL → VIEW, then back to TRAVEL on the next tap. Taps do not queue across phases, and each stop has a minimum view time (`VIEW_TAP_DELAY`). A flight is `travelLegs`: chained cubic Beziers, with an optional via-point and a corkscrew on the first flight. The path is walked by arc length (`travelArc`), so the speed does not jump where legs join. The camera follows `cameraAnchor`, the path averaged over ±`CAM_PATH_WINDOW` s, so tight bends do not whip it. Stops depart along their loop motion (`HOVER_LOOKAHEAD`). If a scenery galaxy sits near the flight line, `pickViaScenery` adds a via-point so the comet swings past it (open-space flights only). Flights that touch the tunnel (`buildTunnelLegs`) use a second leg kind, `{ tunnel: true, s0, s1, endOffset }`: the comet flies the tunnel centreline itself, and the last `TUNNEL_LAND` units blend onto the destination's first stroke point. A departure joins the centreline with `joinLeg` (tangent-continuous, aimed mostly at the join point, `JOIN_HEADING_MIX`). Warp in = GIRAFFE360 → tunnel start → first project; warp out = last project → tunnel exit → landing. The warp (`updateWarp`) is a time bump round the jump point (`WARP_RISE`/`WARP_FALL`): FOV kick, bloom boost (`setBloomBoost`), brighter comet, star streaks, the tunnel fading in (built out ahead of the comet, `WARP_REVEAL_SPEED`) or out, and the outside world switched. Each frame `headS` (the comet's arc parameter, or the stop's in VIEW) moves the tunnel window. The chase distance eases from the departure distance to the destination fit over the first `FOLLOW_EASE` of the path. Project stops: the comet loops round the viz frame (`frameLoopPos`), no auto-rotate. `emitStop('enter')` runs at the end of `enterView`. `emitStop('leave')` runs at the start of `setupTravel`. For stops with a panel (`hasPanel`: rocks and projects), `setupTravel` calls `cam.setScreenShift(true)`, and the fit distance leaves room for the panel (`ROCK_FIT_SIDE`, `ROCK_FIT_BOTTOM`). It owns `worldPos`, the world-space comet head that the camera follows. In VIEW, planar stops first trace their strokes once (`tracing`), then loop (`loopT`). The TEXT stop is special: faster trace (`TEXT_TRACE_DURATION`), the loop is a helix (`helixPos`, `SPIRAL_*`), and after `SPIRAL_DURATION` it calls `setupTravel` itself — no tap. After the landing the tour loops back to stop 1 (the first rock).
- **tunnel.js** — the projects tunnel. The centreline is analytic in a local frame (`setFrame(origin, axis)`): x(s), y(s) are sums of sines (`AMP`, `PERIOD`, random phases), z(s) = s. JS mirrors: `centreWorld`, `tangentWorld`, `frameWorld`, `sOf` (arc parameter of a point), `axisDistance` (placement). The wall is GPU-only: helical strands (`STRANDS`: pitch, handedness, colour) and beaded rings, re-sampled every frame in the vertex shader in a window round the viewer (`setView(s)`, `WINDOW_BACK`/`WINDOW_AHEAD`), so it never ends and no buffer changes. Time motion (all GPU, accumulators in `update(dt)`): each stretch spins back and forth with its own phase (bounded twist), pulses run forward, the radius breathes, and the far tunnel snakes (zero within `WOBBLE_NEAR` of the viewer, so the comet path is static). `TUNNEL_RADIUS` 4.5 keeps the chase camera inside. Warp controls: `setFade`, `setRush`, `setReveal`, and the star streaks (`updateStreaks`). It does not touch the DOM.
- **projectViz.js** — `buildProjectViz(label, { withLabel })` → `{ group, halfW, halfH, update(dt) }`: one live animation per project in a local plane (x right, y up, z to the camera; content within `HALF_W` × `HALF_H`), dim corner brackets as the shared frame. SORTING (the showpiece): real algorithms replayed from recorded compare/swap/write ops, five layouts from the original project (columns, circle, points, spiral, pyramid) morphing between runs. CALCULATOR: grid, three functions plotted by a glowing pen, roots light up. FLOW: rest timer, weekly volume bars, ACWR load lines. Fly-bys: MONTE CARLO (GBM price paths growing on the GPU, a log-normal histogram filling), BALANCER (consistent-hashing ring, requests, failing servers), NEAT (evolving network with flowing signals). Soft ribbons (`ribbon`) for curves that must read well; counts scale with `isMobile`. A short prewarm means no viz starts empty. It does not touch the DOM.
- **attractors.js** — three.js toolkit: scene, camera, renderer, UnrealBloom composer (`setBloomBoost(w)` for the warp), OrbitControls, the `ATTRACTORS` table (derivatives, `dt`, `scale`, `center`, palette; used for palettes and scenery curves), the RK4 integrator, the trail system, and the starfield. The trail is one `THREE.Line` with position/alpha/color attributes (`MAX_POINTS` ring buffer, additive blending). `pushPointWorld` pushes world-space coords into the trail.
- **camera.js** — two modes: `Mode.ORBIT` (target eases to a fixed center, auto-rotate) and `Mode.FOLLOW` (chase camera: `camera = look − chaseDir×dist + up×FOLLOW_UP·dist`, `look = comet + chaseDir×FOLLOW_AHEAD·dist`; `setFollowDistance` is set per flight to the destination's fit distance; the distance spring has a speed cap, `DIST_MAX_SPEED`). All easing uses critically damped springs (`smoothDampScalar`/`smoothDampVec`), so speeds never jump. The chase heading is a yaw and a pitch spring with a speed cap (`TURN_*`), and its pitch stays within `MAX_CHASE_PITCH`, so the view does not spin near the poles. A switch to FOLLOW keeps the current pose and velocity and blends the difference out (`HANDOFF_TIME`; two springs in a row, so the blend starts without a jolt). ORBIT eases the target with `ORBIT_TIME` and keeps its arrival velocity. `setScreenShift(on, immediate)` eases a `camera.setViewOffset` projection shift: the rock moves to the left (side layout) or the top (bottom layout). The orbit target does not move. `isPanelSideLayout()` uses `PANEL_SIDE_QUERY`.
- **stopPanel.js** — self-initialising module. It listens for the `journey:stop` event on `window` and fills the `.stop-panel` element with `textContent` only (no `innerHTML`). `enter` with a panel shows it (adds `.visible` and `body.panel-open`). `leave`, or `enter` without a panel, hides it. Contract: `detail = { phase: 'enter' | 'leave', index, type, panel }`. You can test it from the console by dispatching that event.
- **room.js** — self-initialising module (loaded after `stopPanel.js`). The landing sits inside a Gaussian splat of a real living room (Zip-NeRF "london" scene, CC BY 4.0, reconstructed with gsplat). Assets: `assets/room/room.sog` (7.7 MB, 508k splats) and `room-lite.sog` (5.0 MB, 300k, used when `isMobile`). They load lazily, only when the comet enters the stop `PREFETCH_STOPS_BEFORE` (2) before the landing. The landing is found by `type === StopType.LANDING`, never by index. The room is placed from the landing stop frame (room +X = `stop.right`, +Y = `stop.up`, +Z = `-stop.normal`). The VIEW camera sits at `center - normal * fit`, so the camera lands inside the room near the sofa side, facing the bay windows, and the text floats in front of the windows. `landingFit()` mirrors `orchestrator.fitFor` for the landing: keep them in sync. Tuning: `CAM_LOCAL`, `TEXT_Z` (they set the scale), `FADE_START`/`FADE_FULL` (opacity by camera distance to the room centre, so it is dt-independent; the splat is blurry from outside), `ROOM_BRIGHTNESS` (dims the splat so the glowing text reads) and `BLOOM_THRESHOLD_IN_ROOM`. The SparkRenderer has `renderOrder -10`, so the additive text and trail draw over the splats. It toggles `.room-credit` (shown only at the landing). It needs no changes in orchestrator or camera. `dev/camlog.html` does not load it.
- **intro3d.js** — the 3D intro: extruded name text, LinkedIn and GitHub icons (side by side, with `LINKEDIN_URL`/`GITHUB_URL`), and the rocket with idle loops. Objects live on a world-space anchor, so view rotation moves them with the stars. On the first tap the text and icons stay put. Only the rocket animates: `setRocketCharging` freezes its idle transform and stretches it into the comet streak. `getRocketTipWorld`/`getRocketDirWorld` give the orchestrator the start point and heading.
- **strokeFont.js** — single-stroke vector font and procedural rock outlines (`generateTextLines`, `generateRockWithLabel`). The rock label is capped at 80% of the rock width. They return flat 2D point arrays `{x, y, c}`. `c=0` is a faint pen-travel stroke. `c=1` is a letter stroke. world.js maps them onto a world-space plane.

### Conventions that matter

- **HTML overlays (`.site-nav`, `.stop-panel`)**: they sit over the canvas. main.js must keep ignoring pointer events inside both, or a link click would also advance the journey.
- **Check the room**: `?stop=N` with N = the landing index (last stop; for now 8) shows it. Splats need real frames to sort, so headless Chrome needs about 25 s and SwiftShader flags. Other stops must show no room and make no `.sog` request before the prefetch stop. Do not hard-code the landing index in code.
- **Script order**: in `index.html`, `js/stopPanel.js` must load BEFORE `js/main.js`. With `?stop=N`, `orchestrator.init` dispatches `journey:stop` synchronously. If the listener does not exist yet, the event is lost.
- **Layout query sync**: the media query `(min-width: 700px) and (orientation: landscape)` appears in `css/style.css` (panel at the side) and as `PANEL_SIDE_QUERY` in camera.js (screen shift). Change both together.
- **Brightness via intensity**: `trail.pointIntensity` > 1 writes HDR colors that feed the bloom pass (bold strokes, streak flash). A value < 1 renders faint (connector strokes). See `STROKE_INTENSITY`/`LINK_INTENSITY` in world.js and `TRACE_STROKE_INTENSITY`/`TRACE_LINK_INTENSITY` in orchestrator.js.
- **Palette switches**: set `trail.colorFreezeIdx = trail.pointCount` before changing `trail.attractorIdx`, so drawn points keep their colors.
- **Camera fights**: phases that auto-align the camera (`camAligned` + a spherical glide around the stop toward `textFacePos`) must yield to the user. A `controls` `start` listener sets `camAligned = true` when the user grabs the view. Use this pattern for any new camera steering.
- **Frame-rate independence**: drawing speeds are dt-based (`drawAcc`/`traceAcc` point budgets, sub-stepped curve sampling between `prevT` and `t`). Never use per-frame counts.
- **Starfield**: stars wrap in a cube around the scene center and are re-projected in the vertex shader onto a shell 1x to 10x the camera-to-scene distance, with zoom-relative point sizing. They must always read as far background.
- **Mobile** (`isMobile` in attractors.js): fewer trail points and stars, lower bloom resolution, capped pixel ratio. Keep new effects behind the same scaling.
- Tuning constants live in commented blocks at the top of each module (the "Tuning" section in orchestrator.js, the constants block in world.js). Adjust them there, not inline.
